# Step 2A: authentication and organization membership

The English mobile demo is preserved at `/`, `/students`, `/fees`, `/attendance` and `/more`. Those routes contain only sample records. They are not tenant data pages.

## Configuration

Copy `.env.example` to `.env`, then set values privately. Do not commit or paste credentials into reports. Next.js and `dotenv/config` in Prisma load `.env`; using only `.env.local` does not configure Prisma CLI.

| Variable | Purpose |
| --- | --- |
| `NEXT_PUBLIC_CLERK_PUBLISHABLE_KEY` | Clerk application publishable key (intended for the client). |
| `CLERK_SECRET_KEY` | Server-only Clerk secret key from the same application. |
| `DATABASE_URL` | Neon pooled PostgreSQL connection URL, with TLS; runtime queries through the Prisma Neon adapter. |
| `DIRECT_URL` | Neon direct, non-pooler PostgreSQL connection URL, with TLS; Prisma migrations against the same database. |
| `NEXT_PUBLIC_CLERK_SIGN_IN_URL` | `/sign-in` |
| `NEXT_PUBLIC_CLERK_SIGN_UP_URL` | `/sign-up` |
| `NEXT_PUBLIC_CLERK_SIGN_IN_FALLBACK_REDIRECT_URL` | `/app` |
| `NEXT_PUBLIC_CLERK_SIGN_UP_FALLBACK_REDIRECT_URL` | `/app` |

Enable the desired sign-in methods in your Clerk application. Configure its production domain before deploying. No Clerk Organizations feature, webhook, Neon account provisioning, invitation flow or billing configuration is required for this step. Clerk establishes user identity; local memberships are the authority for organization access.

If Clerk keys are missing, account routes return HTTP 503 instead of allowing unauthenticated access. Public sample routes still work. Database clients are initialized lazily on server-only code paths.

## Install and migrate

Use Node.js 22.12+ (the implementation environment uses Node 22.22.3).

```powershell
cd C:\Users\aojha\school-saas
npm ci
npm run db:validate
npm run db:generate
npm run db:migrate
npm run dev
```

Migration: `20261005000000_organization_membership`.

The migration creates Organization, Membership, two enums, unique organization slug, a composite membership primary key `(organizationId, clerkUserId)`, a user lookup index and a cascading foreign key. The composite primary key enforces the requested unique membership constraint. A user's roles are independent across organizations. Prisma generates IDs and updates `updatedAt`; direct SQL writes must supply these values. No migration has been applied to Neon as part of implementation without a configured connection.

The generated Prisma client is ignored by Git and generated by `postinstall` or `npm run db:generate`. Never run `db push` to substitute for this migration.

## Routes and authorization

- `/sign-in` and `/sign-up`: Clerk's catch-all sign-in/sign-up screens.
- `/app`: signed-in organization picker, queried by the verified Clerk user ID, with a no-memberships empty state.
- `/app/new`: organization form. The Server Action independently authenticates, validates only name/type/slug with Zod and performs an atomic nested write creating the organization and OWNER membership. Browser-supplied identity, role or organization ID fields are ignored. Slugs are trimmed/lowercased and collisions return a field error.
- `/app/org/[organizationId]`: the server validates the ID and fetches the membership using both the verified user ID and organization ID, selecting organization details through that membership. Missing membership and missing organization return the same unavailable response.

Do not rely on the app layout, organization picker, local storage or Clerk organization claims for authorization. Call `requireOrganizationMembership` inside every future data read, action and route handler. Use its returned organization ID to scope queries and its stored role for any future role-specific operation. There are no cross-request membership caches. No student, fee, attendance, Razorpay or subscription backend was added.

Unit tests mock the Clerk and Prisma boundaries to verify authentication, scoped queries, multiple roles, rejected access, forged form fields, input validation and sanitized errors. They do not replace the following live integration checks or prove database rollback behavior by themselves.

## Manual test: two users and two organizations

Use a disposable Neon development database and two separate browser profiles.

1. While signed out, open `/app`, `/app/new` and a copied organization URL. Expect Clerk sign-in and no organization data. Public sample pages remain accessible.
2. Sign up as **User A**. Expect the no-organizations state. Create **Saraswati School** with type SCHOOL and slug `saraswati-kota`. Expect organization A and role OWNER. Confirm one organization and one OWNER membership in the database.
3. Sign up as **User B**. Expect an empty picker. Create **Bright Coaching** with type COACHING and slug `bright-kota`. Expect organization B and role OWNER. Each picker must list only its own organization. Cross-open the other user's organization URL; expect the unavailable response without its name or details.
4. As the trusted development database administrator, insert a membership linking User A's actual Clerk ID to organization B with role ADMIN, and User B's ID to organization A with role STAFF. Supply timestamps for these test SQL writes. Refresh both pickers. A must see OWNER for A and ADMIN for B; B must see STAFF for A and OWNER for B. No UI endpoint for granting memberships exists in this step.
5. Remove B's test STAFF membership in A directly in the development database. Refresh/direct-open A as B: access must be denied and A must disappear from B's picker. A's own access must remain.
6. Try duplicate `saraswati-kota` (including uppercase), invalid slugs, blank/overlong names and a forged type. Expect validation/conflict errors with no partial organization. Submit forged `role`, `clerkUserId` and `organizationId` fields: the created organization must still belong to the session user as OWNER. Try duplicate membership insertion in the database: the composite primary key must reject it.
7. Sign out, then reopen protected URLs and retry a captured creation request. Expect no data/write. Check 360px mobile layout, keyboard form errors, dark mode, sign-out controls and switching organizations. Sample pages must continue to display their demo notice.
